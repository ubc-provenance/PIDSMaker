Datasets¶

PIDSMaker supports the public datasets most used in research on graph-based intrusion detection, of two kinds: provenance datasets, the system events recorded inside hosts, and network datasets, the authentications or flows between the hosts of a network. Every system runs on both kinds, with a few exceptions. This page describes each dataset, its attack scenarios and its ground truth.

Overview¶

Nodes and events are counted in the database of each dataset, before graph construction. Size is the size of its Parquet files, downloaded with pidsmaker download and read in place.

Provenance¶

Nodes are processes, files and netflows, edges are system events, and the ground truth lists the attack nodes. The preprocessed datasets are downloaded from Hugging Face.

Network¶

Nodes are hosts, edges are authentications or network flows, and malicious events are labelled in the database. The databases are built from the preprocessed files of LARES, and downloaded like the provenance datasets.

Dataset Events Hosts Malicious events Size (GB)
LANL 49.3M NTLM authentications 15,610 705 0.40
OPTC_NET 1.86B network flows (1.12B FLOW START) 625 5,165 (1,015 FLOW START)¹ 11.8

¹ With the labels of LARES propagated to all the records of malicious flows (default); 2,370 (115 FLOW START) with the labels of LARES as they are (see OPTC_NET).

Provenance datasets¶

Provenance datasets record the system events of one or several hosts, captured by an audit framework or by EDR telemetry, during benign activity and attack campaigns. Their ground truth lists the nodes involved in each attack (see Ground truth).

DARPA TC¶

The DARPA Transparent Computing program produced benchmark datasets for evaluating provenance-based security systems.

ATLASv2¶

Paper · Two Windows 7 hosts (h1, h2) attacked from Kali Linux. The dataset covers four benign days followed by one attack day on which all ten scenarios are executed. The provided data is Carbon Black Cloud EDR telemetry; the original dataset also includes Sysmon, Windows Security Auditing, Firefox, and DNS logs.

CARBANAKv2¶

Paper · Multi-host testbed comprising four Windows 10 workstations (h1–h4), a CentOS 7 Linux fileserver (fs), and a Windows 10 Server AD domain controller (dc). Benign activity was generated by four graduate students using the machines as their primary workstations. The provided data is Carbon Black Cloud EDR telemetry.

CARBANAKV2_EDR¶

Attack id Duration Description
0 10 days MITRE Carbanak APT emulation. Attacker compromises h1 (Apr 30) via WScript-based Carbanak implant (TransBaseOdbcDriver.js). Pivots to Linux fileserver fs and then Windows AD domain controller dc via lateral movement (May 2). Subsequently spreads to h2, h3, and h4 (May 7–10), establishing persistence across all hosts. 
pidsmaker SYSTEM CARBANAKV2_EDR

PROVENANCE_BENIGN¶

A Linux audit corpus used only to pretrain SPIDER. It has no ground truth, so it can't be used to evaluate detection. It is downloaded like the other datasets (pidsmaker download PROVENANCE_BENIGN, 2 MB).

It is built on a Linux machine: auditd records the system calls of 21 scripted workloads (from core utilities, compilers and package managers to web servers, databases, browsers and attack-like commands), the logs are parsed into entities and edges, and create_database_provenance_benign.py loads them into a PROVENANCE_BENIGN database with the DARPA TC schema. The collection scripts are on the spider branch, and their README describes each step.

The dates of PROVENANCE_BENIGN in DATASET_DEFAULT_CONFIG (pidsmaker/config/config.py) are those of the corpus used in the paper (2026-03-16, UTC). Set them to the days of your own capture.

Network datasets¶

Network datasets record the communications between the hosts of an enterprise network, authentications or flows, during benign activity and a red team campaign. Their single node type is the host, and their events carry attributes (logon types, ports, protocols, sizes...) that become edge features (batching.edge_features=edge_attrs). Both are described by a schema in pidsmaker/config/schemas.py, and both are built from the preprocessed files of LARES (see Building datasets from scratch).

Malicious events are labelled in the database (label column), so the ground truth is event-level: the evaluation labels each edge with its events. Models are trained and validated on benign events only: construction.benign_training (on by default) drops the malicious events of the train and val dates, which has no effect when they have none (as for LANL and OPTC_NET).

LANL¶

The "Comprehensive, Multi-Source Cyber-Security Events" dataset of the Los Alamos National Laboratory: 58 days of authentications between the computers of the LANL network, with the red team events of a penetration test. As in Euler, Argus, Jbeil and LARES, only NTLM authentications are kept. Edges are authentications, typed by their orientation (LogOn, LogOff, ...), with the logon type, authentication type, success and kinds of source and destination users as attributes.

LANL timestamps are seconds from an undisclosed origin, mapped to UTC dates such that the first red team event happens on 2015-01-03. Models are trained on 2015-01-01, validated on 2015-01-02 and tested from 2015-01-03 to 2015-01-30. The root source of the attack is host 9660.

pidsmaker SYSTEM LANL

OPTC_NET¶

The network flows of all the hosts of DARPA OpTC (eCAR FLOW START and FLOW MESSAGE events), from 2019-09-16 to 2019-09-25. Edges are flows, with the source and destination ports (grouped by service and range), the protocol and the size of messages as attributes. As in LARES and Argus, only FLOW START events are used by default (construction.operations). Models are trained from 2019-09-16 to 2019-09-21, validated on 2019-09-22 and tested from 2019-09-23 to 2019-09-25 (malicious flows happen on 2019-09-23 and 2019-09-24). The root sources of the attacks are hosts 201, 402 and 501.

LARES labels only some of the records of each malicious flow (a flow has FLOW START and FLOW MESSAGE events, recorded by the hosts at both ends). By default, the database labels malicious all the records of a malicious flow (same 5-tuple in the same LARES file): 1,015 malicious FLOW START events instead of the 115 of LARES. The labels of LARES are kept by building the database with --no_label_propagation (see Building datasets from scratch, tab OpTC flows)). Euler and Argus use another preprocessing and labelling of OpTC (IP addresses as nodes, including external hosts, and all the events of compromised hosts as malicious), so their results on OpTC are not comparable.

99.9% of the FLOW START events are NetBIOS, LLMNR and SSDP broadcasts and multicasts and ICMPv6 neighbor discovery, which link each host to most hosts in every time window. They are dropped by default (construction.drop_noise_events, which has no effect on other datasets); set construction.drop_noise_events=False to keep them, as LARES does. The OpTC hyperparameters of LARES (30 min windows, α = 5, β = 30) and the 6 min snapshots of Argus are loaded with --tuned (config/tuned_baselines/optc_net/).

pidsmaker SYSTEM OPTC_NET

Train, validation and test splits¶

Each dataset is split by day, as defined by train_dates, val_dates and test_dates in DATASET_DEFAULT_CONFIG (pidsmaker/config/config.py):

  • Train days: benign activity only, used to train the model.
  • Validation days: benign activity only, used to pick the detection threshold.
  • Test days: benign activity and attacks, used for evaluation.

On datasets with labelled events, construction.benign_training enforces it by dropping the malicious events of the train and validation days.

The events of each day are then cut into time-window graphs during construction.

Ground truth¶

The two kinds of datasets are labelled differently:

  • Provenance datasets come with the list of the nodes involved in each attack, in files under ground_truth/. PIDSMaker ships several labelings of the DARPA TC attacks (orthrus, reapr, threatrace).
  • Network datasets label their events in the database. Malicious nodes are the endpoints of malicious events.

See Ground truth for how they are selected and how labels are assigned to nodes, edges and time windows.

Adding custom datasets¶

To add a new dataset, define its configuration in pidsmaker/config/config.py:

DATASET_DEFAULT_CONFIG = {
    "MY_DATASET": {
        "raw_dir": "",
        "database": "my_database_name",
        "database_all_file": "my_database_name",
        "schema": "darpa_tc", # Format of the database: node types, edge types and event attributes (in pidsmaker/config/schemas.py)
        "timezone": "US/Eastern", # Timezone of the dates below
        "start_date": "2018-04-02", # Start date (Inclusive)
        "end_date": "2018-04-14", # End date (Exclusive)
        "train_dates": [
            # Dates/graphs used for training (i.e., benign activity)
            "2018-04-02",
            "2018-04-03",
            "2018-04-04",
            "2018-04-05",
            "2018-04-07",
            "2018-04-08",
            "2018-04-09",
        ],
        "val_dates": [
            # Dates/graphs used for validation/threshold calibration (i.e., benign activity)
            "2018-04-10"
        ],
        "test_dates": [
            # Dates/graphs used for testing (i.e., contains both benign and attack activity)
            "2018-04-06",
            "2018-04-11",
            "2018-04-12",
            "2018-04-13"
        ],
        "unused_dates": [
            # Any unused dates/graphs that should be ignored
             "2018-04-14"
        ],
        "ground_truth_relative_path": ["MY_DATASET/labels.csv"],
        "attack_to_time_window": [
            ["MY_DATASET/labels.csv", "2018-04-11 10:00:00", "2018-04-12 12:00:00"],
        ],
    },
}

schema names a dataset schema of SCHEMAS in pidsmaker/config/schemas.py (darpa_tc, optc, carbon_black_edr, lanl_auth, optc_flows), from which the numbers of node and edge types are derived. A dataset in a new format needs a new schema, which describes the database tables of its node types, its edge types and the attributes of its events.

Then follow the database creation guide to load your data, and add its ground truth under ground_truth/ (or, with a schema that has a label column, label its events in the database, as the network datasets). A dataset with labelled events, like LANL, sets ground_truth_relative_path and attack_to_time_window to empty lists, and can set root_attack_nodes, the root sources of its attacks used by the host-centered evaluation.

# Contributing

PIDSMaker aims to keep up with the latest research on provenance-based and network intrusion detection, and it can only do so with the help of the community. Every contribution is welcome!

## What to contribute

- **A new system**: your published PIDS or NIDS, so that others can benchmark against it. Start with the [tutorial](../guide/tutorial.md).
- **New components**: encoders, decoders, objectives, featurization methods, provenance or network datasets...
- **Fixes to existing systems**: some systems may not perfectly reflect their original implementation.
- **Bug fixes and optimizations**: spotted a slow operation and found a better alternative? Send it!
- **Documentation**: typos, unclear explanations, missing examples. Every page has an :lucide-pencil: edit button.

## Development tips

Install from source
:   Clone the repository and install it in editable mode, with the test dependencies: `pip install -e ".[test]"` (see [Installation](../getting-started/installation.md#1-install-pidsmaker)). Your changes are used without reinstalling.

Avoid concurrent runs from scratch
:   Two runs started at the same time with the same `construction` arguments on the same dataset write to the same folder, which can silently corrupt their outputs. Start the first run, wait until the shared tasks are done, then launch the others. Alternatively, use `--restart_from_scratch`. See [Caching of tasks](../guide/pipeline.md#caching-of-tasks).

Iterate quickly
:   Use a small dataset such as `CLEARSCOPE_E3` or `CADETS_E3`, and `--force_restart=TASK` to re-run only the task you are changing.

## Before opening a pull request

<ol class="pm-steps" markdown>
<li markdown>**Format the code.** The repository uses [ruff](https://docs.astral.sh/ruff/) through pre-commit:

```shell
pre-commit run --all-files
```
</li>
<li markdown>**Run the tests.** Functional tests check that changes to one component don't break the others. Update them when you add a component. They run the pipeline in test mode on a small sample of CLEARSCOPE_E3 (`tests/fixtures/`), written as a temporary Parquet dataset: they need neither the full datasets nor a database server.

=== "GPU"

    ```shell
    pytest tests -n 4                       # in parallel with pytest-xdist
    ```

=== "CPU"

    ```shell
    pytest tests -n 4 --device cpu          # as in the CI
    ```

=== "Full dataset"

    ```shell
    pytest tests -n 4 --db full             # CLEARSCOPE_E3 tests on the full dataset
    ```

=== "Coverage"

    ```shell
    pytest --cov=pidsmaker tests/
    ```

The tests also run on CPU with GitHub Actions on every pull request (`.github/workflows/tests.yml`), on Python 3.9 and 3.11. See [`tests/README.md`](https://github.com/ubc-provenance/PIDSMaker/blob/main/tests/README.md) for all options.
</li>
<li markdown>**Update the documentation.** If you added or changed arguments in `pidsmaker/config/config.py`, regenerate the reference and check the docs locally (see below).</li>
</ol>

## Building the documentation

The documentation is built with [Zensical](https://zensical.org) from the `docs/` folder. Zensical needs Python ≥ 3.10 (≥ 3.11 for the version used by the CI, 0.1.3). With a PIDSMaker environment in Python 3.11, install it there:

```shell
pip install zensical
```

With a PIDSMaker environment in Python 3.9 or 3.10, install Zensical in a separate environment with Python ≥ 3.11.

Then, with PIDSMaker installed from source (the argument reference is generated by importing `pidsmaker`):

```shell
cd docs
./build.sh                          # regenerate the argument reference, then build
zensical serve -a 0.0.0.0:8000      # live preview on http://localhost:8000/PIDSMaker/
```

Zensical reports broken links and anchors at every build: please fix them before opening your pull request.

| What | Where |
|---|---|
| Pages | `docs/docs/**/*.md` |
| Navigation, theme, redirects | `docs/zensical.toml` |
| Styles | `docs/docs/stylesheets/extra.css` |
| Generated argument lists | `docs/scripts/args/`, produced by `docs/scripts/get_arguments.py` |

The site is deployed to GitHub Pages automatically when changes are merged into `main`.

## Releasing a new version

Maintainers release a version by:

1. Updating `version` in `pyproject.toml` (e.g. `5.1.0`) and the release notes of the README, in a pull request.
2. Publishing a [release](https://github.com/ubc-provenance/PIDSMaker/releases/new) on GitHub, with a tag equal to that version (e.g. `5.1.0`).

The release runs `.github/workflows/publish.yml`, which builds the package and publishes it to [PyPI](https://pypi.org/project/pidsmaker/) (it fails if the tag differs from the version of `pyproject.toml`). PyPI trusts this workflow as a [trusted publisher](https://docs.pypi.org/trusted-publishers/), so no token is stored in the repository.
